## 一、它解决什么问题

AI 编程助手有个通病：**每一次对话它都从零开始认识你。**

你昨天说过的技术栈、上周定下的规范、半小时前刚踩过的坑 —— 新开一个会话就全没了。
更糟的是长任务：聊到几十轮之后，它开始忘记最初要做什么，产出越来越偏。

`dsh-memory` 把这件事变成**全自动的基础设施**：

| 问题 | 没有它的时候 | 有它之后 |
|---|---|---|
| **每次都要手动唤起记忆技能** | 忘了唤起 → AI 这次就不"懂你" | 会话开始**自动注入**，零操作 |
| **长任务做到后面忘了最初目标** | 压缩/长对话后跑偏、产生幻觉 | 原始目标**逐字**存档，压缩后与每 N 轮自动重述 |
| **换个项目就"失忆"** | 不知道这个目录是干嘛的、要守什么规矩 | 每个工作区**独立记忆端口**，首次进入自动建好 |
| **任务做完经验没留下** | 下次遇到同样问题重新踩一遍 | 归档闸门逼着沉淀进**跨工作区共享**的长期库 |
| **怕隐私被落盘** | 不知道 AI 偷偷记了什么 | 隐私红线落成**可执行代码**，写入前强制自检 + 脱敏 |
| **不知道 AI 到底记了啥** | 只能一个个文件翻 | 一条命令看**全部工作区**的审计报告 |

**全部数据都是你自己磁盘上的 Markdown 文件。** 没有数据库、没有云同步、没有账号，
用任何编辑器都能读写，删掉插件也照样在。

## 二、和别的记忆方案比，它凭什么不一样

> 这一节是我在写这个插件前**调研了同类项目**之后总结的。如果你只用一句话选它，
> 那就是：**它是唯一把「记忆的四种职责」分开、并且为「跨工作区共享」设计了强制机制的方案。**

### 2.1 三类主流方案，各自的取舍

| 方案类型 | 代表 | 强项 | 代价 |
|---|---|---|---|
| **向量库 / RAG** | mem0、Zep、cognee | 语义检索强，能处理海量碎片 | 需要 embedding 服务或本地模型；引入依赖；**不透明**（你不知道它记住了什么、为什么这么答） |
| **单文件指令** | `CLAUDE.md` / `AGENTS.md` | 简单、直接、人人会用 | 只有一层；**越写越长**，最后没人维护；每次全量注入，token 浪费 |
| **会话记忆插件** | Cline Memory Bank、memory-toolkit、claude-compact-memory | 解决"这次会话别忘事" | 大多**只管当前会话/当前项目**；跨项目共享基本靠手动 |

### 2.2 dsh-memory 的四个结构性差异

#### 差异一：四层**职责分离**，而不是四层文件夹

大多数"多层记忆"是**按容量分**的（热/温/冷、短期/长期）。
dsh-memory 是**按职责分**的 —— 这是它最核心的设计：

```
L1 班长      跨工作区共享的长期知识      ← 只能模型主动写（所以有闸门）
L2 课代表    这个工作区怎么运作          ← 只记稳定事实，不记进度
L3 组长      这个任务做到哪了            ← 插件自动维护
L4 工作日志  本轮原始轨迹                ← 全自动，可丢
```

**为什么这个区分重要**：它划出了**唯一真正需要跨工作区共享的那一层**（L1）。
其他方案常见的失败模式是"什么都在一个文件里"，于是：
- 项目进度和用户偏好混在一起 → 换项目时携带一堆无关信息
- 每条记忆都要判断"该不该全局共享" → 模型无从下手
- 没有一个层是"共同的大脑" → 换个项目就重新认识你

dsh-memory 明确：**L2 记「这个工作区怎么运作」，L3 记「这个任务做到哪了」，
L1 记「关于用户和可复用的知识」，L4 自动记录。**
每个文件都只回答一个问题，所以每层都能保持精简。

#### 差异二：为「跨工作区共享」加了**强制机制**

这是 dsh-memory 独有的。调研中我发现同类方案的共同盲点：
**它们都假设模型会自觉把经验写进长期库 —— 而实测中模型几乎不会。**

真实的失败链条是这样的：

```
模型一路更新任务进度（那是 L3，自动的）
        ↓
从不回头沉淀"可复用的结论"
        ↓
任务完成、归档
        ↓
经验困在本工作区的 archive/ 里
        ↓
换个项目 → 完全看不到，下次重新踩坑
```

dsh-memory 用**两道机制**封住这个漏洞：

| 机制 | 时机 | 行为 |
|---|---|---|
| **归档闸门** | 调用 `archive_task` 时 | 本任务从未写过 L1 → **拒绝归档**，要求先判断一次（可用 `skipGlobalCheck: true` 明确跳过） |
| **L1 轮询** | 每 4 轮（可配） | 仍未写过 L1 → 提醒一次，并说明"这是唯一跨工作区共享的一层" |

两者都有护栏（已写过就不提醒 / 同轮只提醒一次 / 走冷却期），**不会变成骚扰**。
效果是把"经验沉淀"从**靠自觉**变成**流程必经点**。

> 同类方案里，只有少数提到了"定期整理记忆"（如 `agent-memory` 的 sleep-time
> Manage 层、`memory-toolkit` 的 handoff），但它们都是**建议**，不是**闸门**。

#### 差异三：按「token 性价比」分层，而不是全量注入

`CLAUDE.md` 那类方案是**每次全会话注入**。文件一长，成本线性上涨，而且
"注入得越多 ≠ 效果越好"。

dsh-memory 的分层预算：

| 层 | 注入什么 | 上限 |
|---|---|---|
| L1 | **只给**入口指针 + 10 条画像 + 读取指南 | 1.4 KB |
| L2 | 本工作区**速览**（定位/规范），详述按需读 | 2.2 KB |
| L3 | 任务目标 + 验收 + 最近进度 | 1.6 KB |
| L4 | **完全不注入**（需要时用工具读） | 0 |

**总计约 6 KB ≈ 1500–2000 token**，而且是"索引 + 按需检索"而不是全量。

研究依据：
- **Chroma《Context Rot》(2025)** —— 18 个模型实测，~300 token 的聚焦输入**优于**
  ~113k 全量输入；原因是全量迫使模型同时做检索与推理
- **《Lost in the Middle》(TACL 2023)** —— 相关信息放在上下文**开头或结尾**时
  召回率最高，放中间显著下降 → 所以目标锚点插在消息靠前位置

#### 差异四：**零依赖、零进程、纯 Markdown**

| | dsh-memory | 向量库方案 | 独立守护进程方案 |
|---|---|---|---|
| 运行时依赖 | **0**（只用 Node 内置模块） | 向量库 + embedding | 常驻服务 |
| 需要的服务 | 无 | 需要 API key 或本地模型 | 需要启动/保活 |
| 数据形态 | **纯 Markdown** | SQLite / 向量索引 | 数据库 |
| 可读性 | 人直接读 | 需要工具查询 | 需要工具查询 |
| 卸载后数据 | **照样能用** | 需要导出 | 需要导出 |

这不是"功能更少所以更简单"—— 而是刻意的取舍：**记忆是你要保留十年的东西，
它不应该依赖任何会过期的基础设施。** 详见[第十六节](#十六设计取舍)。

### 2.3 一张表说清差异

| 能力 | `CLAUDE.md` 式 | 会话记忆插件 | 向量库方案 | **dsh-memory** |
|---|---|---|---|---|
| 自动读取（无需手动唤起） | ✅ 全量注入 | ⚠️ 部分 | ✅ | ✅ 索引 + 按需 |
| 自动写入 | ❌ 手动 | ⚠️ 会话级 | ✅ | ✅ 三层自动 + 一层闸门 |
| 跨工作区共享 | ⚠️ 手动同步 | ❌ 多数不管 | ✅ | ✅ **带强制机制** |
| 长任务防遗忘 | ⚠️ 靠文件 | ⚠️ 会话级 | ❌ 不解决 | ✅ **四重保险** |
| 归档 / 任务生命周期 | ❌ | ⚠️ 部分 | ❌ | ✅ |
| 跨工作区审计 | ❌ | ❌ | ❌ | ✅ |
| 隐私红线可执行 | ❌ | ❌ | ❌ | ✅ |
| 零依赖 | ✅ | ✅ | ❌ | ✅ |
| 数据是纯文本 | ✅ | ✅ | ❌ | ✅ |
| 自带测试 | ❌ | ⚠️ | ✅ | ✅ **13 套 / 450+ 断言** |

### 2.4 什么情况下**不该**用它

诚实地说，它不是万能的：

- **你的记忆量极大（几万条以上）** → 关键词检索会不够用，该上向量库。
  dsh-memory 的 `memory_search` 是逐行打分，记忆库在几百到几千条时最合适。
- **你要多台机器同步** → 本插件不管同步。把记忆库放进 Git / 网盘目录是可行的
  （它就是一堆 Markdown），但合并不是自动的。
- **你用的不是 DSH** → 目前只支持 DSH。核心逻辑（`store.js` / `brief.js` /
  `audit.js`）与平台无关，移植到 Claude Code / Codex 的 hooks 模型理论可行，
  但目前没做。

## 三、班级分工：四层各管什么

用「班级」来理解这套设计：

```
        ┌──────────────────────────────────────────┐
        │  你 = 班主任                              │
        │  偶尔检查：干得怎么样？按时归档了吗？       │
        │           有没有写错文件？                 │
        └────────────────────┬─────────────────────┘
                             │  memory_audit（一键总览）
   ┌─────────────────────────┴──────────────────────────┐
   │                                                     │
┌──▼───────────────┐  ┌────────────────┐  ┌──────────────▼──┐
│ L2 课代表         │  │ L3 小组组长     │  │ L1 班长          │
│ 工作区记忆端口    │  │ 任务档案        │  │ 全局记忆库        │
│                  │  │                │  │                  │
│ 这个工作区是做什么 │  │ 当前任务目标    │  │ 关于你这个人的    │
│ 要守哪些规矩      │  │ 验收标准        │  │ 一切：身份/偏好/  │
│ 踩过哪些坑        │  │ 进度时间线      │  │ 技术栈/目标/雷区  │
│ 有哪些里程碑      │  │ 关键约束        │  │                  │
│                  │  │                │  │ ★ 所有工作区共享  │
│ 每工作区一份      │  │ 每任务一份      │  │ 全局唯一一份      │
└──────────────────┘  └────────────────┘  └──────────────────┘
                             │
                    ┌────────▼─────────┐
                    │ L4 个人工作日志   │
                    │ 会话轨迹          │
                    │ 本轮做了啥/啥成果  │
                    │ 可丢，不影响其它层 │
                    └──────────────────┘
```

### 职责边界不能串岗

| 层 | 角色 | 管什么 | **不管什么** |
|---|---|---|---|
| **L1** | 班长 | 关于**你这个人**的长期信息，跨工作区共享 | 某个具体项目的进度 |
| **L2** | 课代表 | 本工作区的**稳定事实**：定位、规范、踩坑、里程碑 | **任务进度**（那是组长的活） |
| **L3** | 小组组长 | **当前任务**的目标、验收、进度、约束 | 跨任务的长期结论 |
| **L4** | 工作日志 | 本轮的原始轨迹，供回溯 | 一切需要长期保留的东西 |

> **为什么强调这个**：本项目开发早期，L2 里有一节叫「进行中与已完成的任务」，
> 和 L3 的职责重叠 —— 同一个任务状态写在两个文件里，一旦不同步就互相矛盾，
> 归档时也不知道该以哪个为准。**现在明确：进度只写 L3。**
> 这个教训也写进了测试里。

### 各层落在哪里

```
L1  <memoryRoot>\                        ← 默认 <DSH_HOME>\memory
      MEMORY.md                          ← 入口索引（画像/读取指南/条目统计）
      00-隐私红线.md                     ← 写入前的硬性红线
      01..NN-*.md                        ← 分类文件（可自由增删）
      12-记忆维护日志.md                 ← 变更流水

L2  <工作区>\.dsh\memory\WORKSPACE.md    ← 本工作区专属
L3  <工作区>\.dsh\memory\ACTIVE.md       ← 当前任务
    <工作区>\.dsh\memory\archive\        ← 已完成任务
L4  <工作区>\.dsh\memory\sessions\       ← 会话轨迹（默认留最近 40 份）
```

## 四、自动化发生在什么时候

| 时机 | 触发点 | 做什么 | 花 token 吗 |
|---|---|---|---|
| **会话开始** | `agent/session-start` | 建立工作区端口；交代四项职责 | 否 |
| **每一步之前** | `agent/pre-step` | 注入记忆简报 / 目标锚点 | 注入占上下文 |
| **每轮结束** | `agent/turn-stopping` | 采集进度、写轨迹、条件式提醒、**L1 轮询** | 采集**零** token |
| **上下文压缩后** | `compaction/end` | 标记下一轮**立即**重述目标 | 否 |
| **归档时** | `memory_write action:archive_task` | **归档闸门**：没沉淀过 L1 就拦下 | 否 |

### 会话开始时会明确交代「四项职责」

每次新对话/新任务，插件都会在简报里逐项告诉模型**它要维护哪四份东西**，
以及哪些是自动的、哪些必须它主动写：

```
### 你的四项职责（要维护的四份东西）

① L1 班长（全局库）—— 你主动写
   关于用户本人的长期信息、跨项目可复用的结论 → target:"global" + category
   ⚠️ 这是唯一跨工作区共享的一层；你不写，别的项目就永远看不到。

② L2 课代表（本工作区）—— 你主动写
   本工作区的稳定事实：做什么的、守什么规矩、踩过什么坑、有什么里程碑
   注意：不要把任务进度写这里，那是 L3 的事。

③ L3 小组组长（当前任务）—— 插件自动维护，你只在关键处补
   插件每轮自动记进度、压缩后自动重述目标；你负责设目标/记决定/归档。

④ L4 工作日志（会话轨迹）—— 全自动，你无需管
```

### 目标怎么保证不被忘记（四重保险）

1. **逐字保留** —— 会话里第一条实质用户消息（非寒暄）被**原样**写进 ACTIVE.md，之后只增不改
2. **压缩感知** —— 上下文被压缩后，下一轮**立刻**重新注入原始目标
3. **周期重述** —— 默认每 10 轮重述一次，对抗长对话中的目标漂移
4. **位置优先** —— 锚点插在消息靠前位置（研究显示开头/结尾的召回率最高）

> 连续做多个任务也没问题：每次归档后，下一个任务会从归档点**之后**
> 重新寻找自己的目标，不会张冠李戴。

### 两道防漏机制：归档闸门 + L1 轮询

L2/L3/L4 都由插件自动维护，**只有 L1 必须靠模型主动写** —— 而它恰恰是
**唯一跨工作区共享**的一层。

| 机制 | 时机 | 行为 |
|---|---|---|
| **归档闸门** | 调用 `archive_task` 时 | 若本任务从未写过 L1 → **拒绝归档**，要求先判断一次；确实没内容可带 `skipGlobalCheck: true` 跳过 |
| **L1 轮询** | 每 4 轮（可配） | 若本任务仍未写过 L1 → 提醒一次，并说明"跨工作区共享"这件事 |

```yaml
archiveGate: true          # 归档闸门
l1PollEveryTurns: 4        # 每 N 轮检查一次；0 = 关闭
```

> **实现上有坑**：闸门拒绝后，那次 `archive_task` 调用**不能**被当成"任务已归档"
> 来推进任务边界 —— 否则前面写过的 L1 会被划到"上一个任务"，闸门就会再次拒绝，
> **陷入死循环**。所以成功的归档会带一个机器可读标记，边界只在看到它时才推进。
> 这条有专门的回归测试（见第十三节事故 #8）。

## 五、省 token 的六条设计

| 手段 | 说明 |
|---|---|
| **只注入索引** | L1 不注入全文，只给入口指针 + 10 条画像 + 读取指南 |
| **分层预算** | 每层独立字节上限，超限即截断并注明"按需再读" |
| **零 token 采集** | 轮次/工具/文件改动直接读会话事件，不调用模型 |
| **零 token 压缩感知** | 从压缩事件得知，不需要模型汇报 |
| **不注入子代理** | 子代理短命且任务聚焦，注入是纯浪费 |
| **提醒有冷却** | 唯一额外花 token 的机制，限每轮一次 + 每 N 轮一次 |

**注入总量上限 6000 字节**（约 1500–2000 token），可配。

### 关于那个提醒

它是**唯一**会额外花 token 的机制（一次提醒让模型多跑一步）。
即使关掉它，三重保障仍在：系统提示词指引 + 锚点末尾提醒 + 机械进度采集。

```yaml
steerOnHarvest: false   # 极致省 token
l1PollEveryTurns: 0     # 也关掉 L1 轮询
```

## 九、配置

在 profile 的 `cordis.patch.yml` 里加一行，覆盖任意字段：

```yaml
- id: memory
  name: 'dsh-memory'
  config:
    # ---- 路径 ----
    memoryRoot: 'D:\我的记忆库'     # 留空 → <DSH_HOME>/memory（不存在则自动建骨架）
    workspaceDir: '.dsh/memory'     # L2/L3 在工作区里的位置
    sessionRoot: ''                 # 留空自动用 <DSH_HOME>/sessions

    # ---- 自动读取 ----
    autoRead: true                  # 会话开始注入简报
    injectIntoSubagents: false      # 不向子代理注入（省 token）

    # ---- 目标锚定 ----
    autoAnchor: true
    anchorEveryTurns: 10            # 每 N 轮重述；0 = 只在压缩后

    # ---- 自动沉淀 ----
    autoHarvest: true               # 每轮机械采集（零 token）
    steerOnHarvest: true            # 条件式沉淀提醒（唯一额外花 token 的项）
    steerCooldownTurns: 6           # 两次提醒最小间隔
    steerMinToolCalls: 3            # 触发提醒所需的最少工具调用
    harvestMinToolCalls: 2          # 记进度所需的最少工具调用

    # ---- L1 保障 ----
    archiveGate: true               # 归档闸门
    l1PollEveryTurns: 4             # 每 N 轮检查一次；0 = 关闭

    # ---- 预算（字节）----
    maxInjectBytes: 6000            # 单次注入硬上限
    portInlineBytes: 2200           # L2 速览
    globalInlineBytes: 1400         # L1 索引
    anchorInlineBytes: 1600         # L3 锚点

    # ---- 其它 ----
    privacyGuard: true              # 隐私红线自检（强烈建议开启）
    tools: true                     # 注册 memory_* 工具
    diagnostics: true               # 注册 /memory/* 路由
    keepSessionLogs: 40             # 会话轨迹保留份数
    persistTrajectory: true
```

### 自定义分类文件

想加自己的分类（比如「健身记录」）：

1. 在 `memoryRoot` 下新建 `15-健身记录.md`（照抄任一分类文件的结构即可）
2. 在 `MEMORY.md` 的索引表里加一行
3. 在 `lib/tools.js` 的 `GLOBAL_CATEGORIES` 里加映射：
   ```js
   fitness: { file: '15-健身记录.md', label: '健身记录' },
   ```
   这样模型就能用 `memory_write target:"global" category:"fitness"` 写进去。

## 十一、消息来源格式（DSH 插件开发者必读）

> 这一节是给**写 DSH 插件的人**看的。我踩了这个坑，希望你别再踩。
> 如果你只是使用者，可以跳过。

DSH 使用 **V4 会话格式**。写路径的准入检查 `assertV4MessageSources`
要求消息的 `source.kind` 是**生产者自有 kind**，并**显式拒绝** `kind === 'plugin'`：

```
format v4 message requires a producer-owned source kind
```

命中时的表现是**整轮失败**（界面显示「本轮运行失败」，错误码 UNKNOWN）。

| 写法 | 结果 |
|---|---|
| `{ kind: 'plugin', plugin: '任意名' }` | ⛔ 已退役，写路径被拒，**整轮失败** |
| `{ kind: 'plugin:<插件名>' }` | ✅ 命名空间形式（本插件采用） |
| `{ kind: '<自有生产者名>' }` | ✅ 如 `agent-instructions` |

**最容易踩的坑**：DSH 第一方包的源码里能看到
`createUserMessage({ source: { kind: 'plugin', plugin: 'dsh-xxx' } })` 这种写法，
而且 `producerKind()` 里有一张白名单（含 `agent-instructions`、`time-context`、
`goal` 等 30 个名字）会把 `plugin` 映射成生产者 kind。

**但那是「读取旧 V3 文件时的迁移逻辑」，不是写路径的豁免名单。**
照抄第一方插件的写法，你的插件就会在注入消息时整轮失败。

```js
// ✅ 正确
const SOURCE = { kind: 'plugin:dsh-memory' }
agent.inject(createUserMessage({ content: [...], source: SOURCE }))
```

本插件把这条规则固化成了回归测试（`tests/source-format.mjs`），
另有一个 `tests/audit-installed-plugins.mjs` 可以扫描你已装的全部插件找同类问题。

## 十二、隐私红线

`00-隐私红线.md` 的规则已落成**可执行代码**（`lib/privacy.js`），写入前强制自检。

### 硬红线（不可绕过，命中即拒绝并脱敏）

身份证号、手机号、邮箱、银行卡号、API Key/Token/私钥、密钥赋值语句、
内网 IP、门牌号、精确出生日期（仅在"出生"语境附近判定）、学号工号社保号。

### 软红线（默认整类不记录）

人际关系/家庭、医疗健康、生物特征、他人隐私、政治宗教性取向等敏感属性。

### 两个设计要点

1. **误报比漏报更危险**。命中即脱敏的机制会让正常内容被替换成占位符，
   而用户和模型都无从察觉。真实事故：早期密钥规则的"两字母前缀 + 12 位以上"
   把普通英文驼峰命名（`skipGlobalCheck`）误判成密钥，静默替换掉一句完整的技术说明。
   现在收紧了形态约束（必须带分隔符且含数字），并**列出被替换的具体片段**，
   让误报可见、可纠正。

2. **脱敏后没有实质内容就拒绝写入**，而不是往库里塞一句空话。

### 自定义规则

规则表在 `lib/privacy.js` 顶部的 `PATTERNS`（硬红线）与 `SOFT_RULES`（软红线）。
加一条硬红线：

```js
{
  id: 'my-rule',
  category: '凭证与密钥',
  note: '公司内部工单号',
  re: /TICKET-[0-9]{6}/g,
}
```

`/memory/rules` 可以导出当前全部规则，便于核对。

## 十五、常见问题

**Q：装完没反应？**
A：插件只在 DSH 启动时加载。**先重启 DSH**，然后跑 `/memory/ping` 确认。

**Q：`/memory/ping` 404？**
A：说明插件没加载。检查三处部署是否都在（`plugins/`、`node_modules/`、
`package.json` 的 bundles 列表），详见[第六节](#六安装)。

**Q：记忆库会在哪里？**
A：默认 `<DSH_HOME>/memory`（Windows 通常是 `C:\Users\<你>\.dsh\memory`）。
想在别处就在配置里写 `memoryRoot`。

**Q：会不会泄露隐私给模型？**
A：注入的内容只有索引与摘要，且写入前会过隐私红线自检。
但请注意：**注入的内容会进入模型上下文**，这是"让 AI 懂你"的必要代价。
敏感信息的设计原则是"不落盘"，而不是"落盘了但不上传"。

**Q：能跨机器同步吗？**
A：插件不管同步。但记忆库就是一堆 Markdown，放进 Git / 网盘目录即可，
注意多机同时编辑可能会冲突。

**Q：会不会很费 token？**
A：注入上限 6000 字节（约 1500–2000 token），只在会话开始/压缩后/每 N 轮。
机械采集零 token。唯一额外花 token 的是沉淀提醒，可以用
`steerOnHarvest: false` + `l1PollEveryTurns: 0` 完全关掉。

**Q：支持多语言吗？**
A：界面文案是中文，但记忆内容与代码注释不限定语言。

## 十六、设计取舍

写这个插件时做过几个**刻意的选择**，这里说明理由：

### 为什么不用向量库？

**记忆是要保留十年的东西，它不应该依赖任何会过期的基础设施。**

向量库能提供更好的语义检索，代价是：需要 embedding 服务或本地模型、
数据变成不透明的二进制索引、卸载后难以迁移、调试时看不到"它到底记住了什么"。

本项目选择**关键词逐行打分**（`memory_search`）。记忆库在几百到几千条时，
关键词检索的实际效果足够好，而且：你随时可以用编辑器打开看、用 grep 搜、
用 Git 做版本管理。如果哪天你的库大到关键词不够用，`store.search()` 是
唯一需要替换的方法，其余部分不受影响。

### 为什么坚持纯 Markdown？

同上。另外还有一个理由：**可审计性**。
当 AI 说"我记得你说过 X"时，你应该能打开文件确认它记的到底是不是 X。
向量库里你做不到这件事。

### 为什么注入这么少？

因为**注入得多 ≠ 效果好**。研究结论（第五节）显示聚焦的小输入优于全量注入。
更重要的是：全量注入会鼓励"什么都往里塞"，最后变成一个没人维护的巨型文件 ——
这是 `CLAUDE.md` 类方案最常见的失败模式。

### 为什么要做闸门这么一个"会拦人"的机制？

因为实测发现**模型不会自觉沉淀跨工作区经验**。
这不是模型的错 —— 它的注意力在"完成当前任务"上，
而"把经验写到另一个目录"是一件没有即时反馈的事。

闸门把这个动作变成流程必经点，并且给了**体面的跳过路径**
（`skipGlobalCheck: true`），避免"确实没内容"时被卡住。

### 为什么提示词用中文？

因为开发者的母语是中文，而**提示词是要被维护的**。
让维护者能一眼看懂、随时改，比"看起来更国际化"更重要。
代码注释同样。
